# TikTok 达人助手

**在达人主页完成比较与素材整理，在当前视频旁处理评论翻译和字幕。**

研究达人时，我经常在几种操作之间来回切换：打开主页看视频表现，点进作品确认内容，复制链接到下载工具，再去别处整理字幕和评论。数据在页面里，操作却散在不同工具中，换一条视频还要重新判断当前结果属于谁。

这个 Chrome Manifest V3 扩展把这些动作放回浏览器。主页上的视频卡片提供数据和选择入口，当前视频通过悬浮界面与侧栏处理下载、字幕和翻译。提取、页面状态、异步任务和文件输出分别实现，便于维护 TikTok 动态页面中的各种变化。

当前扩展源码版本为 `0.1.28`，主线采用 Chrome-only 构建。仓库还保留早期后端、授权服务与打包代码；了解浏览器主线时可以先从 `extension/` 开始。

## 两种工作场景

### 看达人主页：把一组作品放在一起比较

打开主页后，扩展从页面可见数据、结构化数据和桥接信号中整理视频条目。在已读取的作品范围内，进行排序、筛选、多选和素材下载。

一个典型整理过程是：

1. 打开目标达人主页，等待页面加载出需要研究的作品。
2. 查看卡片数据与商业披露等证据，区分已知字段与缺失字段。
3. 选择有参考价值的作品，指定视频或音频输出。
4. 单项保存，或将所选作品写入批量 ZIP。
5. 根据逐项结果补查失败项目，而不是把整批按钮点完当作全部下载完成。

这里的范围是当前页面已经取得的条目。页面没有加载的历史作品、账号权限以外的内容和失效媒体地址，不能从本地列表直接推断为可取得。

### 看当前视频：字幕与评论跟随播放对象

当前视频流程关心的是结果归属。字幕优先尝试平台文本；需要时再启动浏览器语音识别。评论翻译处理页面正在呈现的评论，侧栏保存字幕与目标语言的译文，并提供预览和导出。

从 A 视频切到 B 视频之后，A 的识别可能仍在运行，页面 DOM 也可能复用了原来的节点。因此当前视频标识、会话缓存和异步结果检查参与整个流程，不能只看“侧栏里有没有文字”。

## 功能结构

| 功能 | 实现内容 | 需要关注的条件 |
| --- | --- | --- |
| 页面数据 | DOM、结构化内容、页面桥接与条目注册 | TikTok 页面结构和已加载范围 |
| 主页工具栏 | 排序、筛选、卡片覆盖层和批量选择 | 字段缺失与作品条目归属 |
| 下载 | 媒体解析、任务队列、命名、文件保存与 ZIP | 可取得的媒体地址、浏览器文件权限 |
| 当前视频 | 活动视频判断、悬浮数据与会话切换 | 单页应用导航、页面节点复用 |
| 评论翻译 | 评论提取、翻译请求、结果显示与重复处理 | 网页接口可用性、限流与语言 |
| 字幕 | 平台文本、浏览器识别、缓存与导出 | 模型准备、音频可取得范围 |
| 双语结果 | 原字幕与按目标语言保存的译文 | 当前视频与翻译任务匹配 |

公开版移除了硬编码翻译 API Key。需要自行配置授权的 HTML 翻译通道在缺少配置时跳过，其余网页翻译路径保留。网页接口依赖外部服务，不能保证一直可用。

## 扩展各部分如何配合

```text
TikTok 页面
  ├─ 内容脚本：工具栏、卡片、评论与当前视频
  ├─ 页面桥接：读取页面侧可见信号
  └─ 提取与注册：规范化条目、证据和缺失字段
         │
         ├─ 活动视频会话 → 字幕侧栏 → 原文 / 译文缓存与导出
         ├─ 翻译请求 → 提供方与队列 → 结果归属检查
         └─ 下载描述 → 媒体解析 → 文件保存 / ZIP

背景脚本：扩展消息与后台服务协调
侧栏：长时间识别、字幕预览和用户操作
```

页面 UI、提取层与下载层不是同一个模块。比如调整主页选择器时，不必同时改 ZIP 写入；调整字幕持久结构时，也不应改变主页作品的排序口径。

Chrome-only 主线将浏览器能力作为主要路径，早期本地后端与云授权代码保留在其他目录。两种模式的依赖和测试条件需要分开理解。

## 动态页面中比较难处理的几个问题

### 1. DOM 还在，视频已经换了

TikTok 的单页导航和滚动视频会复用节点。`ActiveVideoSession` 使用视频键与页面 URL 管理当前上下文，观察到切换时清理当前缓存，记录切换情况。

`activeVideo.ts` 负责判断活动视频；条目注册层组织已经提取的数据。页面内容与异步结果要与会话对应，旧结果不能因为请求晚完成就覆盖新视频。

这类判断依赖真实页面信号，页面实验和地区差异仍可能影响识别。源码中的防护需要实际安装后验证，不能用单个 DOM 测试证明所有页面切换都正确。

### 2. 同一个字段有多个来源

作品信息可能来自可见 DOM、结构化对象和页面数据。提取模块分开处理这些来源，再进行规范化与证据整理。

缺失字段保留为空，不因为界面需要展示就自动补成零。商业披露与内容推断也不应混为一谈：有商品相关信号，不等于已经证明这条作品有付费合作。

对维护者来说，遇到错误数据时应先检查来源和解析规则，再检查显示层；不能仅在 UI 上改一个默认值掩盖问题。

### 3. 识别和翻译会比页面停留更久

浏览器字幕识别需要准备模型、取得音频并运行推理。用户可能在过程中切换视频、取消翻译、重新打开侧栏或改变语言。

侧栏流程分别管理识别、取消和新视频排队。翻译有请求标识、队列与响应结构检查，部分路径还会等待结果并处理超时。将这些状态明确下来，是为了区分“还在处理”“已经取消”和“当前结果不属于这条视频”。

首次模型下载与后续缓存读取也属于不同阶段。没有完成模型准备，不能显示为已经生成字幕。

### 4. 缓存可复用，也需要限制

字幕缓存按视频 ID 保存，译文按目标语言组织。持久结构带版本号，恢复时检查字段、片段、数字与文本容量。

当前校验限制包括：单视频最多 10,000 个片段、文本容量检查上限 1,000,000 字符、最多保存 20 种译文语言。它们是结构约束，并不说明所有浏览器都能无压力运行这么大的识别任务。

缓存读取失败时应丢弃无效结构，不能把损坏的存储内容继续当作字幕。对应实现可看 [subtitleSessionCache.ts](extension/src/sidepanel/subtitleSessionCache.ts)。

## 下载工作流：解析、输出与逐项结果

下载从一个明确的媒体描述开始，之后分别处理地址解析、字节读取、文件名称和保存目标。主页卡片队列与批量限制管理提交节奏，文件写入模块负责最终输出。

批量 ZIP 使用独立写入器。每项素材分别记录成功或失败，完成后返回归档名、成功数、失败数和失败明细；归档写入本身出错时中止写入。这个区分有助于判断是某一条媒体不可取得，还是整个目标文件保存失败。

| 阶段 | 代码入口 |
| --- | --- |
| 卡片排队与批量限制 | [cardQueue.ts](extension/src/downloads/cardQueue.ts)、[batchLimit.ts](extension/src/downloads/batchLimit.ts) |
| 媒体地址解析 | [tiktokMediaResolver.ts](extension/src/downloads/tiktokMediaResolver.ts) |
| 浏览器下载流程 | [browserWorkflow.ts](extension/src/downloads/browserWorkflow.ts) |
| 文件命名与目标选择 | [naming.ts](extension/src/downloads/naming.ts)、[filePicker.ts](extension/src/downloads/filePicker.ts) |
| ZIP 写入 | [zipWriter.ts](extension/src/downloads/zipWriter.ts) |

下载质量取决于页面暴露的资源与当前授权范围；扩展没有提供获取账号无权访问内容的能力。素材后续使用还需要自己的授权。

## 字幕路径怎样选择

平台已经有时间轴字幕时，优先解析平台文本，减少重复识别与模型下载。没有合适文本时，浏览器 Whisper 路径按需准备模型和音频。

Transformers.js 用于浏览器模型能力，运行库和模型有各自的下载与缓存需求。处理长视频会占用浏览器内存与计算资源，首次使用时间不能与已有缓存时混为一谈。

字幕导出与识别也是两步：识别结果保留片段和时间戳，导出时再按格式组织。最终应对照音频复核专有名词、数字和句子边界；字幕存在不代表每个词都正确。

## 安装与开发

建议 Node.js 20+ 和 pnpm。当前浏览器主线的构建方式为：

```powershell
cd extension
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
$env:TDA_CHROME_ONLY_BUILD = '1'
pnpm build
Remove-Item Env:\TDA_CHROME_ONLY_BUILD
```

在 Chrome 的 `chrome://extensions/` 打开开发者模式，加载 `extension/dist`。重新构建后，需要重新加载扩展并刷新已打开的 TikTok 页面；只更新文件不一定会替换已有页面中的内容脚本。

首次体验建议按顺序确认：页面数据能否读取、当前视频归属是否正确、单项文件能否保存、平台字幕是否可用，再尝试浏览器识别和批量下载。不同阶段失败时，定位到相应模块会更容易。

## 仓库阅读路线

```text
extension/
  src/content/       页面工具栏、桥接、会话、评论与卡片
  src/extractors/    活动视频、多来源提取与规范化
  src/registry/      视频条目注册
  src/downloads/     队列、媒体解析、命名与 ZIP
  src/translation/   翻译请求与队列
  src/sidepanel/     字幕、浏览器识别和缓存
  src/background/    扩展后台协调
  tests/             提取、状态、下载与侧栏用例
backend/             早期本地服务实现
license-worker/      早期云授权服务
packaging/           早期分发与安装辅助
scripts/             构建与检查入口
```

想看动态页面状态，可以先读 [session.ts](extension/src/content/session.ts) 与 [activeVideo.ts](extension/src/extractors/activeVideo.ts)；想看数据证据，从 [extractors/](extension/src/extractors/) 和 [evidence.ts](extension/src/content/evidence.ts) 开始；字幕和翻译流程主要在 [sidepanel/index.ts](extension/src/sidepanel/index.ts) 与 [foregroundQueue.ts](extension/src/translation/foregroundQueue.ts)。

## 当前验证结果与待处理问题

2026-10-07 的公开源码检查结果如下：

| 检查 | 实际结果与范围 |
| --- | --- |
| TypeScript | 通过扩展类型检查 |
| 默认 Vitest 配置 | 40 个文件，329 个通过、6 个跳过 |
| Chrome-only 构建 | 构建成功 |
| Chrome-only 完整测试 | 320 个通过、15 个失败 |
| 六个浏览器专用侧栏用例 | 每个在独立 Vitest 进程中运行时通过 |

测试主要使用 happy-dom、模拟 Chrome 消息、替代网络与模型。Chrome-only 完整套件的失败集中在字幕、翻译和切换视频断言；测试同时包含后端路径与浏览器路径，并共用侧栏状态。独立用例结果提示模式和共享状态影响了测试，但没有消除整套测试的 15 项失败，源码与测试也没有为此被改成跳过。

真实 TikTok 页面安装、浏览器模型推理、真实下载、本地服务与云授权端到端流程尚未验收。详细命令、失败范围和单用例复现方式见 [检查记录](docs/verification.md)。

这个项目公开的是当前实现与可检查的测试状态。后续维护重点包括真实页面回归、测试模式隔离、平台字段变化和浏览器长任务的资源表现。
